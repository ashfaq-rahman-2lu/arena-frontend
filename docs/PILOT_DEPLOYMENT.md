# Zero-budget pilot: Cloudflare Pages Free frontend

The API is independently deployed on Render Free with Neon Free PostgreSQL. Requests follow this path:

```text
Browser → https://YOUR-PROJECT.pages.dev/api/*
        → Cloudflare Pages Function
        → https://YOUR-API.onrender.com/api/*
        → Neon PostgreSQL
```

The frontend repository contains `functions/api/[[path]].ts`. It forwards request bodies, signed cookies, CSRF and Origin headers, and preserves upstream `Set-Cookie` and OAuth redirects. It follows no redirects itself and prevents API responses from being cached. The upstream is fixed by server-side configuration, not chosen by browser input.

## Cloudflare Pages setup

1. Push this frontend repository to your Git host and connect it to a Free Cloudflare Pages project.
2. Use the repository root as the project directory.
3. Build command: `npm ci && npm run build`.
4. Build output directory: `dist`.
5. Set build `NODE_VERSION=24.21.0`.
6. Leave `VITE_API_BASE_URL` empty for this pilot. The browser must call `/api` on Pages.
7. Set the Pages Functions runtime variable `API_ORIGIN=https://YOUR-API.onrender.com` for production, and redeploy after changing it.
8. Set the backend's `FRONTEND_URL` to this project's exact HTTPS Pages origin. If enabling Google, use `https://YOUR-PROJECT.pages.dev/api/v1/auth/google/callback` as its callback URL.

`wrangler.jsonc` describes this Pages build and compatibility date. Set its name to your actual Pages project if using Wrangler deployment. Dashboard/Git integration is sufficient; no Cloudflare API token belongs in browser code.

`public/_routes.json` restricts Functions invocations to `/api/*`; static pages/assets do not need proxy invocations. Pages supplies its default SPA fallback because this build has no top-level `404.html`. Use Pages Git integration or Wrangler deployment so the Functions directory is compiled; a static-files-only upload is insufficient.

Production cookies remain signed, HttpOnly, Secure, and SameSite=Lax on the Pages domain. Do not set `VITE_API_BASE_URL` directly to the unrelated Render domain for this cookie-session pilot.

## Previews and local tests

The backend accepts one exact frontend origin. Do not point arbitrary Pages preview domains at the production API; use a separate test API/database and matching `FRONTEND_URL` for previews.

The standard browser suite tests the Vite proxy. `BROWSER_DIRECT_API=true` tests a separate API origin. `BROWSER_USE_PAGES=true` runs the real local Pages Functions runtime through Wrangler, using the same dedicated backend fixture server. No Cloudflare account or paid provider call is needed for local checks.

## Free-service limits

Pages Functions share the Workers Free request quota (currently 100,000/day); static requests remain free and unlimited when they do not invoke Functions. Public pages poll every 15 seconds while visible, so watch API request usage as pilot audience grows. Keep Workers on the Free plan. When quota is exhausted, choose fail-closed behavior for Functions in the dashboard rather than falling back to static content on API routes.

Render's first request after idle may take about a minute. The proxy preserves redirects and allows a 90-second upstream timeout, then returns a safe retry message. Render HTML wake-up pages are also converted into a safe JSON gateway error for `/api/v1/*` requests. Actual cloud deployment and credentials still need account-side setup.

## Diagnosing API gateway failures

The JSON message "The API is waking up or unavailable" is generated by the Pages Function when its upstream request fails or returns HTML for an API route. It does not identify the underlying cause, and a request that fails before reaching NestJS will not produce a backend request error log.

After deploying the proxy, open the current Cloudflare Pages deployment's **View details → Functions** log stream before reproducing the failing request. Alternatively, from an authenticated terminal, run:

```sh
npx wrangler pages deployment tail --project-name YOUR-PROJECT --format=json
```

Pages Functions logs are streamed live and are not retained by this logging feature. See [Cloudflare's logging instructions](https://developers.cloudflare.com/pages/functions/debugging-and-logging/).

Gateway failures emit a JSON `api_proxy_failed` event with `requestId`, method, pathname, elapsed milliseconds, and a reason:

- `invalid_configuration`: `API_ORIGIN` is missing, invalid, or points back to Pages. The response is 503.
- `upstream_html`: the upstream returned an HTML response for an API route. The event includes its status and configured origin. This can be a wake-up page, an unavailable-service page, or the wrong upstream host; the client receives 502.
- `upstream_http_error`: the upstream returned HTTP 429 or 5xx without triggering the HTML guard. The event includes its status and configured origin. Its status, headers, and streamed body continue to pass through to the client unchanged apart from the existing gateway cache and request-ID headers.
- `upstream_request_failed`: fetching or handling the upstream response threw. The event includes the configured origin and a safe error type, such as `TimeoutError`. The client receives 502.

Upstream HTML and HTTP-error events also include validated diagnostic headers when available: `upstreamContentType` (normalized media type only, with parameters removed), `upstreamRetryAfter` (numeric seconds or an HTTP date), and `upstreamCfRay` (the upstream Cloudflare Ray ID). Missing or malformed values are omitted. An HTML 429/5xx generates one `upstream_html` event with the original `upstreamStatus` and the client-facing `statusCode: 502`; it does not generate a duplicate HTTP-error event. Non-HTML 429/5xx responses are logged without reading or cloning their bodies. Successful responses, redirects, and other ordinary non-HTML 4xx responses do not generate failure events.

The proxy forwards a validated or generated `X-Request-ID` to the API and returns it in the response, including gateway errors. Use that header to correlate a failing browser request with the gateway event and any backend error. Use `upstreamCfRay`, when present, with the failure timestamp to help the provider trace an upstream rejection; it is distinct from the outer Pages request's Ray ID. Cookies, authorization headers, query strings, request/response bodies, unselected headers, content-type parameters, and raw exception messages are excluded from gateway events.

Verify that the deployed `API_ORIGIN` matches the API service's public origin, without `/api` or another path. Check its `/api/v1/health` endpoint directly and through the Pages origin separately. Inspect Render startup and service events if the direct request fails; inspect Pages configuration and Function logs if only the proxy fails. A healthy endpoint now does not prove that an earlier request succeeded.
